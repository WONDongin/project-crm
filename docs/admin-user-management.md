# 관리자 계정 관리와 담당자 예외 처리

## 실행 전 적용

- 기준 브랜치: dev. 기존 고객·상담·첨부 기능의 실제 검증은 사용자 확인 기준 완료 상태다.
- 이번 기능은 users.auth_version 컬럼을 사용한다. ddl-auto=none이므로 애플리케이션 실행 전에 `backend/db/migrations/20261107_user_auth_version.sql`을 MySQL에 한 번 적용한다. 이미 컬럼이 있으면 재실행하지 않는다. 실제 사용자 DB에 이 SQL을 실행하지 않았다.
- 기존 users.email UNIQUE는 그대로 사용한다. 비밀번호는 BCrypt로 저장한다.
- 배포 이전 JWT에는 uid/ver claim이 없으므로 배포 후 모든 사용자가 다시 로그인해야 한다.

## 계정 API

| 요청 | 동작 |
|---|---|
| GET /admin/users | 이름·이메일 검색, 역할·상태 필터, 서버 페이징·메모·현재 담당 고객 수 |
| POST /admin/users | 이메일·이름·비밀번호·역할·전공·상태·메모로 계정 생성 |
| PATCH /admin/users/{id} | 이메일·이름·역할·전공·상태·메모 수정 |
| POST /admin/users/{id}/password | 지정한 새 비밀번호로 초기화 |
| DELETE /admin/customers/{id}/counselor | 고객 담당자만 명시적으로 해제 |

- 역할·전공·상태는 각각 USER_ROLE/USER_SPECIALTY/USER_STATUS의 활성 코드로 검증한다. 역할은 프로젝트의 ROLE_ADMIN/ROLE_CONSULTANT만 허용한다.
- 이메일은 앞뒤 공백 제거·소문자 정규화 후 중복을 검사하고 DB UNIQUE로 동시 저장 충돌도 차단한다.
- 비밀번호는 8~20자다. 수정 API에는 비밀번호가 없으며 초기화 전용 API를 사용한다.
- 비밀번호·해시·인증 버전은 사용자 목록이나 변경 응답에 노출하지 않는다.
- 본인의 역할을 관리자에서 바꾸거나 본인을 비활성화하는 요청은 409로 거부한다. 마지막 활성 관리자 해제도 차단한다.
- 사용자 변경 응답은 user/releasedCustomerCount/reauthenticationRequired를 반환한다. 본인 이메일 변경·비밀번호 초기화 후에는 로그아웃하고 다시 로그인한다.

## 담당자 정책

- 상담사가 ACTIVE가 아니게 되거나 ROLE_CONSULTANT가 아니게 되면 해당 사용자의 담당 고객을 모두 미배정으로 전환한다.
- 고객 상태·최근 상담일·기본 정보·과거 상담 작성자·신청 원문·첨부 그룹은 유지한다.
- 계정 재활성화 또는 상담사 권한 재부여 시 고객을 자동으로 다시 배정하지 않는다.
- 직접 배정 해제는 전용 DELETE 요청으로 처리한다. PATCH 요청에서 담당자 누락/null은 여전히 400이며 암묵적으로 배정을 해제하지 않는다.
- 배정 요청은 저장 시점에 활성 상담사인지 다시 검증한다.
- 계정 비활성화·역할 변경 화면에서는 현재 목록의 담당 고객 수와 함께, 저장 시점의 담당 고객 전체에 적용된다는 안내를 확인한다. 실제 해제 건수는 서버 응답을 사용한다.

## 인증 및 동시 변경

- JWT에는 uid(사용자 ID), ver(인증 버전)를 포함한다. 매 요청 DB의 사용자 ID·이메일·역할·ACTIVE 상태·인증 버전을 확인한다.
- 이메일·역할·상태 변경과 비밀번호 초기화 때 auth_version을 증가시킨다. 재활성화하거나 원래 역할로 되돌려도 이전 토큰은 다시 유효해지지 않는다.
- 이름·메모·전공 수정만으로는 인증 버전을 변경하지 않는다.
- 로그인은 사용자 행을 잠그고 마지막 로그인 시각을 저장해 계정 변경과 값이 덮어쓰이지 않도록 한다.
- 계정 관리·담당자 배정 변경은 사용자를 ID 순으로 잠근 뒤 고객을 잠근다. 작은 운영자 목록을 기준으로 계정 변경을 직렬화하는 구조이며, 계정 수가 크게 늘면 별도 관리 잠금 전략을 검토한다.
- 상담사 변경 작업과 파일 접근도 사용자 공유 잠금 후 고객 잠금 순서를 사용한다. 시스템 신청 기록 저장도 담당 사용자 공유 잠금을 먼저 획득한다.
- 데이터베이스 잠금 경합이 관리 API에서 발생하면 409와 재조회 안내를 반환한다. 실제 MySQL 동시성 부하 검증은 아직 진행하지 않았다.
- 미인증·폐기된 JWT는 보호 API에서 401, 인증된 다른 역할은 403이다. /auth/me의 미인증 요청도 401로 처리한다.

## 화면

- 관리자 사용자 목록에서 계정 생성·수정·비밀번호 초기화 모달을 제공한다.
- 필수값·비밀번호 확인·배정 해제 확인, 저장 중 중복 요청 차단, 실패 시 입력 유지, 목록 새로고침을 지원한다.
- 본인의 역할·상태 선택은 비활성화한다. 서버에서도 같은 보호 조건을 검사한다.
- 고객 목록에서는 배정 해제 확인·취소 후 요청하고 고객 상태는 그대로 표시한다.
- 관리자 화면은 작은 화면에서 메뉴를 상단에 배치하고 표는 내부에서 가로 스크롤한다. 네이티브 dialog의 키보드 포커스와 Escape 닫기를 사용하며 저장 중에는 닫지 않는다.

## 검증 결과

- TypeScript와 변경 프론트 파일 ESLint 통과.
- 외부 Google Fonts 호출만 임시 제외한 production 빌드 통과. 원래 폰트 소스는 복구했고 폰트 변경을 포함하지 않는다.
- 전체 Java 파일 JDK 문법 파싱 검사 통과. 의존성 해석·Lombok 처리·백엔드 컴파일·테스트 통과를 의미하지 않는다.
- 모의 API 브라우저 통과: 계정 생성, 이메일 중복 오류 시 입력 유지, 비활성화 확인과 실제 해제 건수 표시, 비밀번호 불일치·초기화, 본인 권한 보호, 모달 취소/Escape, 배정 해제·취소, 본인 초기화 후 로그인 이동.
- 1440/768/390px 화면 확인, 가로 넘침과 브라우저 런타임 오류 없음.
- 백엔드 통합/MVC/JWT 필터/서명 테스트 추가: 암호화·중복·상태/역할 변경 후 미배정 전환·원본 보존·초기화·재활성화 후 예전 버전 거부·접근 역할·인증 ID/버전 claim 등을 포함한다.
- Gradle 배포본 다운로드가 Network is unreachable로 실패하여 새 백엔드 테스트를 실행하지 못했다. 새 기능의 MySQL 연동·동시 요청과 이전 기능 회귀 확인은 추가 실행 검증이 필요하다.

## 사용자 목록 검색·페이징 추가

`GET /admin/users`의 data는 배열에서 페이지 객체(content/number/size/totalElements/totalPages)로 변경했다. 상세 조건과 화면 동작은 [admin-user-search.md](admin-user-search.md)를 참고한다.
