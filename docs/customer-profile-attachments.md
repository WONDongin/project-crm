# 고객 기본 정보 수정 및 상담 첨부파일

## 기존 DB 확인 및 연락처 형식 정리

기존 `customers(phone, birth_date)` 복합 UNIQUE와 `birth_date NOT NULL` 제약을 사용한다. **새 컬럼이나 인덱스를 추가하는 DDL은 필요 없다.** 연락처는 `01011111111`처럼 숫자만 저장한다.

1. 신규 상담 신청과 고객 정보 수정은 서버에서 연락처 형식을 검증한 뒤 숫자만 저장한다. 기존 연락처의 하이픈·공백은 조회 시에도 제거하여 비교한다.
2. 기존 연락처의 일괄 정리는 별도 데이터 관리 작업이다. 이번 변경은 실제 고객 정보를 일괄 변경하지 않는다. 기존 데이터의 형식 정리가 끝나기 전에는 기존 UNIQUE가 표기가 다른 번호의 동시 중복까지 막아주지는 않는다.
3. 기존 `file_mng`와 `activity_logs.file_upload_no`를 사용한다. 새 첨부 테이블이나 BLOB 컬럼은 만들지 않는다.
4. `ATTACHMENT_DIR`의 기본값은 백엔드 실행 위치 기준 `./uploads/attachments`다. 정적 리소스로 공개하지 않으며 DB와 함께 백업한다. 다중 인스턴스에서는 같은 영속 볼륨을 사용한다.
5. 파일 10MB, 요청 11MB를 허용하도록 multipart 제한을 맞춘다.

삭제된 확인용 SQL 파일은 복원하지 않았다. 실제 DB에 UPDATE나 DDL을 실행하지 않았다. 이전 버전의 generated column 추가 ALTER TABLE은 필요 없다.

## 엔티티·기본값과 실제 DDL

- `Customer`: 기존 복합 UNIQUE(phone, birth_date), birth_date NOT NULL을 엔티티에도 선언한다.
- `User`: specialty NOT NULL을 선언하고, 테스트 사용자에게 실제 전공 값을 입력한다.
- `Code`: 복합 키, 필수값, 길이, CHAR(1)을 DDL에 맞춘다. 깊이 0·사용 여부 Y·생성일은 애플리케이션에서 초기화한다. 이름은 임의로 채우지 않고 필수값으로 검증한다.
- `ActivityLog`: 고객·내용·생성일을 필수로 선언하고, 생성 주체 SYSTEM·결과 RECEIVED 기본값을 설정한다.
- `FileMeta`: 삭제 여부 N·등록일을 애플리케이션에서 초기화한다.
- H2 테스트는 엔티티로 테이블을 생성하므로 필수값·복합 중복 제약을 검사할 수 있지만, 실제 MySQL의 collation, DEFAULT, ON UPDATE, 잠금 동작을 대신하지 않는다.
- 사용자 확인 기준으로 실제 DB에 `users.email` UNIQUE 설정을 완료했다. 엔티티의 이메일 중복 금지 선언과 DB 제약이 일치한다. `ddl-auto=none`이므로 다른 환경에서도 해당 제약 존재 여부를 확인한다.

## 입력과 동시 저장 보완

- 상담 신청의 이름·이메일·코드·내용 길이를 저장 컬럼에 맞춰 제한한다.
- 신청의 상담 유형·관심 과정·희망 시간·유입 경로를 활성 공통 코드로 검증한다.
- 동일 신규 고객의 동시 신청으로 UNIQUE 충돌이 발생하면 409로 응답한다. 자동 재시도나 이력 병합은 하지 않는다.
- 관리자의 담당자 변경도 고객 조회 시점부터 같은 고객 행에 비관적 쓰기 잠금을 사용한다.
- activity_logs.updated_at은 DB에서 생성 시에도 채워지고 내용 외의 갱신도 반영하므로 화면은 이를 '최근 갱신'으로 표시한다.

## 고객 기본 정보

- PATCH /consultant/customers/{customerId}/profile
- 요청: name(필수, 최대50), phone(필수, 서식 포함 최대20), interestCourse(활성 공통 코드).
- 현재 담당자인 활성 상담사만 수정. 저장 시 고객 행 잠금 후 배정 재검증.
- 연락처는 숫자 9~11자리로 정규화한다. 기존 서식이 있는 DB 값도 하이픈/공백/괄호/마침표/+를 제거한 값으로 비교한다.
- 연락처 + 생년월일 기준 중복 검사(자기 자신 제외), 중복은409. 기존 연락처 형식 정리 후 기존 `UNIQUE(phone, birth_date)`로 동시 저장 중복도 차단한다. 생년월일은 기존 DB의 NOT NULL 정책을 사용하며 대체 날짜나 별도 비교 컬럼은 필요 없다.
- 상담 신청도 정규화된 연락처와 생년월일로 기존 고객을 찾아 수정 후 재신청이 같은 고객에 누적되도록 보완.
- 이름·연락처·관심 과정만 변경. ActivityLog 신청 원문, 생년월일, 상태, 담당자, 최근 상담일 유지.

## 첨부파일

경로: /consultant/customers/{customerId}/activities/{activityId}/attachments

- GET: `file_mng` 메타데이터 목록. 실제 파일은 목록 조회 시 읽지 않는다.
- POST: multipart/form-data, file 파트 1개. 생성 파일 ID 반환(201).
- GET /{fileId}: 다운로드, Content-Disposition attachment, UTF-8 파일명, nosniff, no-store.
- DELETE /{fileId}: `del_yn=Y`, `updated_at` 갱신. 삭제 파일은 목록과 다운로드에서 제외한다. 실제 파일은 보존하며 물리 삭제는 별도 보존 정책으로 처리한다.

지원: PNG/JPG/JPEG/GIF/WEBP, PDF, UTF-8 TXT, DOCX/XLSX/PPTX. HWP, DOC/XLS/PPT, ZIP, 실행파일은 지원하지 않는다.

- 파일당10MB, 기록당10개. 빈 파일 거부.
- 파일명에서 경로/제어문자 제거, 최대200자.
- 요청 MIME을 신뢰하지 않고 확장자와 매직 바이트 검사. TXT는 UTF-8·제어문자, Office 문서는 내부 ZIP 필수 파일 검사.
- Office 검사 중 엔트리2000개, 전체 해제100MB 초과 거부. 파일 내부 문서를 렌더링하거나 실행하지 않음.
- 형식 검사는 악성코드 백신 검사를 의미하지 않는다.
- 현재 담당자는 과거 작성자의 첨부도 목록 조회/다운로드 가능.
- 추가/삭제는 현재 담당 고객 + 본인 작성 CONSULTANT 기록만 허용. SYSTEM 원본 변경 차단.
- 고객/기록/파일 ID 조합을 매번 검사. 고객 행 잠금으로 배정 변경과 개수 제한 검사 직렬화.
- `activity_logs.file_upload_no = file_mng.file_upload_no`와 `file_category='activity_logs'`로 연결한다. 기존 그룹 번호는 유지하고, 첫 업로드 시 그룹 번호가 없으면 양수 난수를 생성하여 기존 그룹과 중복 여부를 확인한다.
- `file_seq`(파일 ID), `file_nm`(원본명), `file_save_nm`(UUID 저장명), `file_path`(저장 폴더), `file_size`, `del_yn`, `created_at`, `updated_at`을 기존 컬럼에 매핑한다. MIME은 파일명으로 응답하며 신규 업로드 내용은 기존 헤더 검증을 통과해야 한다.
- 신규 파일은 설정 폴더 바로 아래 저장하며 `file_path='.'`를 기록한다. 기존 파일의 상대 경로는 설정 폴더 기준으로 해석한다. 절대 경로는 설정 폴더 내부에 있을 때만 허용한다. 기존 경로·카테고리 값이 이 규칙과 일치하는지 적용 전에 확인한다.
- 업로드 DB 트랜잭션이 롤백되면 방금 저장한 파일도 정리한다. 커밋 결과 불명 또는 프로세스 강제 종료 시에는 파일이 남을 수 있으므로, DB에 연결되지 않은 파일의 정리는 별도 운영 작업이다.
- 논리 삭제는 본문을 즉시 제거하지 않아 롤백 시 복구 가능하다. 삭제한 파일은 10개 제한에서 제외한다.
- 기존에 잘못된 안내를 따라 `activity_attachments`를 생성했더라도 이 변경은 기존 테이블이나 데이터를 삭제하지 않는다. 해당 테이블에 이미 실제 첨부가 있다면 이관을 먼저 검토해야 한다.

## 화면

고객 상세 기본 정보 하단에 수정 폼. 각 상담 기록 하단 첨부파일 보기를 열어 목록을 조회하고 업로드/다운로드/삭제.

저장/업로드 중 연속 클릭 차단, 오류 시 입력/선택 유지, 삭제 확인·취소, 권한 거부(403) 시 화면 차단. 파일·상담 기록 없음(404)은 첨부 영역에서 안내하며 고객 화면을 유지한다. 파일 작업 404 후 목록을 재조회하고, 안내는 재조회 성공 후에도 유지한다. 이미지 인라인 미리보기는 제공하지 않고 다운로드 방식 사용.

## PR 재검토 보완

- 파일 작업의 404와 권한 거부 403을 구분한다. 404는 첨부 영역에 안내하고 목록을 다시 조회한다. 목록 조회의 404도 고객 화면 전체를 차단하지 않는다.
- 목록 조회 오류와 작업 오류를 분리해 자동 재조회 성공이 파일 누락 안내를 즉시 지우지 않도록 한다. 사용자가 다시 조회하면 오류를 초기화하고 새 결과를 확인한다.
- 심볼릭 링크 검증은 일반 파일 읽기·경로 이탈 검증과 분리한다. 링크 생성 권한이나 지원이 없으면 해당 링크 테스트만 건너뛰며, 저장소 검증 실패는 그대로 테스트 실패로 처리한다.
- PR의 삭제된 SQL 파일·추가 고객 인덱스 적용 안내를 제거하고, 이메일 UNIQUE 설정 완료 상태를 반영한다.
